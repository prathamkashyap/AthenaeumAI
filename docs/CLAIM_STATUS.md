## 2. Observed Architecture

Actual current control flow, not intended flow.

### 2.1 Background queue topology

One BullMQ queue, one consumer process.

- Queue name `athenaeum-background-jobs` — `backend/utils/jobQueue.js:6`, duplicated as a literal
  in `backend/worker.js:23`.
- Producer: `createJobQueue` in `backend/utils/jobQueue.js:33-79`.
- Default job options (`jobQueue.js:11-17`): `attempts: 3`, `backoff: { type: "exponential",
  delay: 2000 }`, `removeOnComplete: { count: 500, age: 7d }`, `removeOnFail: { count: 500,
  age: 30d }`. Per-call overrides honoured for `attempts`, `backoff`, `deduplicationId`
  (`jobQueue.js:56-62`).
- Consumer: `processBackgroundJob` in `backend/worker.js:46-107`, registered by `startWorker` at
  `worker.js:109-155` with `concurrency: 5` (`worker.js:126`) plus `QueueEvents` listeners for
  `completed`, `failed`, `stalled` and SIGINT/SIGTERM graceful shutdown.
- `startWorker` runs only when `worker.js` is the entry module (`worker.js:157-164`).
  **`backend/server.js` never starts the worker.** The API process and the worker process are
  separately deployed containers that must both be running for background work to occur.
- Routing is by the `data.type` string, not by the BullMQ job name. The job name is a
  human-readable label only.
- Serialization guard: enqueueing a function payload throws `QueueEnqueueError` before BullMQ is
  contacted (`jobQueue.js:35-39`). Enqueue failures are wrapped in `QueueEnqueueError`
  (`jobQueue.js:69-77`), so every enqueue call site decides independently whether to surface or
  swallow that error.

### 2.2 Job type traces

There are exactly three job types, three enqueue sites, and one worker dispatch chain.

#### `INDEX_MATERIAL`

| Aspect | Observed |
| --- | --- |
| Enqueue location | `backend/controllers/quizController.js:105-110` |
| Job name (label) | `` `RAG Index Material: ${material.title}` `` |
| Payload | `{ type: "INDEX_MATERIAL", data: { materialId } }` |
| Options | `deduplicationId: index-material:${material._id}` |
| Awaited? | **Yes** — `await` before `res.json` (`quizController.js:121`) |
| Processor | `backend/worker.js:51-64` |
| Work performed | `StudyMaterial.findById` → `indexStudyMaterialChunks(material)` → returns `{ type, materialId, chunkCount }` |
| Retry | 3 attempts, exponential backoff 2s |
| Idempotency | **Convergent.** `indexStudyMaterialChunks` upserts on `(user, studyMaterial, chunkIndex)` and then deletes chunks with `chunkIndex >= chunks.length` (`embeddingService.js:98-134`), so re-running produces the same chunk set. |
| Failure mode | Material missing or zero indexable chunks throws (`worker.js:54-61`), retried 3×, then retained as a failed job for 30 days. |

#### `SYNC_ATTEMPT`

| Aspect | Observed |
| --- | --- |
| Enqueue location | `backend/controllers/quizController.js:282-291` |
| Job name (label) | `` `Sync Attempt Analytics & Rebuild Queue - User ${req.user._id}` `` |
| Payload | `{ type: "SYNC_ATTEMPT", data: { attemptId, userId, quizId } }` |
| Options | `deduplicationId: sync-attempt:${attempt._id}` |
| Awaited? | **Yes** — `await` before `res.json` (`quizController.js:300`) |
| Processor | `backend/worker.js:66-98` |
| Work performed | Loads attempt + quiz; re-validates `String(attempt.user) !== String(userId)` (`worker.js:79-81`); then `updateUserProgressFromAttempt` → `recordAttemptEvents` → `enqueueFailedQuestionItems` (if `score < total`) → `rebuildReviewQueueForUser` |
| Retry | 3 attempts, exponential backoff 2s |
| Idempotency | **Idempotent for its transactional effects; convergent for the rest.** `syncAttemptOnce` takes a conditional per-attempt claim inside `runInTransaction` (`worker.js:59-63`) and applies `updateUserProgressFromAttempt` and `recordAttemptEvents` in that same transaction (`worker.js:72-81`), so a failure anywhere inside rolls the claim back together with the progress writes already issued. A redelivery whose claim already committed reapplies nothing. `enqueueFailedQuestionItems` and `rebuildReviewQueueForUser` deliberately sit *after* the commit and are replayed on every delivery (`worker.js:164-170`, `:179`, `:193`), converging because the queue is written by upsert (`reviewQueueService.js:8-25`). Exercised against a real replica set by `backend/tests/integration/attemptSyncTransaction.test.js`. This is duplicate-*processing* protection only: it does nothing about a client submitting a second attempt. |
| Failure mode | The attempt is already committed when the job is enqueued, so a terminal job failure leaves progress permanently out of sync with the attempt. |

#### `REBUILD_REVIEW_QUEUE`

| Aspect | Observed |
| --- | --- |
| Enqueue location | `backend/services/recommendationService.js:37-47` |
| Job name (label) | `` `Rebuild Review Queue - User ${userId}` `` |
| Payload | `{ type: "REBUILD_REVIEW_QUEUE", data: { userId } }` |
| Options | `deduplicationId: rebuild-review-queue:${userId}` |
| Awaited? | **No** — fire-and-forget: `void jobQueue.enqueue(...).catch(...)`, failure logged as a warning and swallowed (`recommendationService.js:37-47`) |
| Processor | `backend/worker.js:100-104` → `rebuildReviewQueueForUser(userId)` |
| Retry | 3 attempts, exponential backoff 2s |
| Idempotency | **Partially convergent.** `upsertOpenQueueItem` upserts on `{ user, itemType, topic, status: "open" }` plus source keys (`reviewQueueService.js:8-25`), and a unique partial index over `{ user, itemType, topic, source.quiz, source.attempt, source.flashcardSet, source.flashcardId }` with `partialFilterExpression: { status: "open" }` backs it at the database level (`models/ReviewQueue.js:70-84`). Re-running with unchanged inputs converges. It is an upsert, not a reconcile: items whose source condition has disappeared are never removed, closed, or expired. |

**Note on the type string.** The actual job type is `REBUILD_REVIEW_QUEUE`, not
`REVIEW_QUEUE_REBUILD`. It appears as `REBUILD_REVIEW_QUEUE` in `worker.js:100`,
`recommendationService.js:38`, and `bullmq.test.js:111`.

**Observed flow — upload / quiz generation**

```
POST /api/v1/quiz/generate
  → multer disk write                                    (synchronous)
  → extractTextFromPDF: fs.readFileSync + pdf-parse      (SYNCHRONOUS, in-request)
  → generateQuizFromAI  → Groq llama-3.3-70b-versatile   (SYNCHRONOUS, in-request, 3 sequential calls)
  → runInTransaction: StudyMaterial.create + Quiz.create (committed)
  → jobQueue.enqueue(INDEX_MATERIAL)  [awaited]          (chunk + embed + write happens here, in the worker)
  → StudyMaterial.linkedQuizzes.push + save
  → res.json 200
```

`fs.readFileSync` at `backend/utils/pdfParser.js:16` is a blocking read. Text extraction
(`quizController.js:49`) and LLM generation (`quizController.js:61`) both complete before the
response. Only the chunk/embed/write stage is deferred. There is no `202 Accepted`; the handler
returns `200` with the full quiz body (`quizController.js:121-128`).

**Observed flow — attempt submission**

```
POST /api/v1/quiz/:id/attempt
  → Quiz.findOne scoped to { user | isDefault }
  → normalize answers, grade against quiz.answer
  → analyzeMistakesForAttempt → Groq llama-3.3-70b      (SYNCHRONOUS, in-request, up to 5 items)
  → QuizAttempt.create (user, quiz, answers, mistakeAnalyses)
  → quiz.attempts.push + quiz.save
  → jobQueue.enqueue(SYNC_ATTEMPT)  [awaited]
  → res.json 200

worker, SYNC_ATTEMPT:
  → updateUserProgressFromAttempt   (mastery / confidence / weakness / streak)
  → recordAttemptEvents              (LearningEvent.insertMany)
  → if score < total: enqueueFailedQuestionItems   (reuses the stored analyses; only calls
                                                  analyzeMistakesForAttempt again if the array is empty)
  → rebuildReviewQueueForUser
```

**Observed flow — retrieval read path**

```
POST /api/v1/tutor/ask  (or /ask/stream)
  → gatherTutorContext
      → searchMaterialChunks
          → ensureChunksForUser      (SYNCHRONOUS lazy indexing on the READ path)
          → MaterialChunk.find({ user, [studyMaterial] }).populate().lean()   (whole user corpus into Node)
          → score every chunk in-process, sort desc, slice(limit)
      → UserProgress.findOne → weak topics
      → QuizAttempt.find({ user, mistakeAnalyses non-empty }).limit(8)
      → FlashcardSet.find({ user }).limit(10)
  → generateTutorResponseFromAI  → Groq llama-3.3-70b-versatile
      (or streamTutorResponse → SSE)
  → recordLearningEvent(ai_tutoring_interaction, metadata.retrievedChunkIds)
  → response with retrievedContext[]
```

`ensureChunksForUser` is invoked on **every** search (`embeddingService.js:179`) and will
synchronously chunk, hash, and bulk-write any material for that user that has zero chunks. If the
`INDEX_MATERIAL` job has not run yet, the first tutor query pays the full indexing cost inside the
HTTP request.

**Citations.** `askContextualTutor` returns `retrievedContext[]` containing `sourceNumber`,
`chunkId`, `studyMaterialId`, `sourceTitle`, `chunkIndex`, `score`, `preview`, and `topics`
(`tutorService.js:172-181`). The same chunk ids are persisted to
`LearningEvent.metadata.retrievedChunkIds` (`tutorService.js:164`, and
`tutorController.js:173` for the streaming route). The frontend renders these entries and
displays `Math.round(source.score * 100)` as a match percentage (`src/pages/Tutor.tsx:189-196`).
There is no page number, character offset, or sentence-level span.

**Refusal behaviour.** `searchMaterialChunks` applies no minimum score. `askContextualTutor`
always invokes the LLM (`tutorService.js:141-148`). When no chunk matches, the prompt receives
the literal string `"No matching uploaded material chunks were found."`
(`aiQuizService.js:533`, `streamingTutorService.js:67`) alongside the system-level instruction
*"If context is insufficient, explain what is missing and suggest a Socratic study strategy"*
(`aiQuizService.js:518`). That is a prompt-level soft instruction, not a code-level gate. The only
conditional response, `fallbackTutorResponse` (`tutorService.js:9-38`), is reached only when the
LLM call itself throws (`tutorService.js:149-152`); it emits the "I could not find enough indexed
source material" wording only when `materialContexts` is empty. Grading of the interaction is by
result count, not by confidence: `result: materialContexts.length ? "completed" : "partial"`
(`tutorService.js:158`, `tutorController.js:167`).

Retention decay here is **linear** (−2.2 per day), not exponential. The only exponential term in
the system is the mastery recency factor in `progressService.js:25`.

`backend/services/recommendationService.js` computes a **second, divergent** set of the same
quantities: `readinessFor` = `mastery × 0.55 + confidence × 0.30 + (100 − weakness) × 0.15`
(`:12-18`) and `retentionTrend` = `confidence − days × 2.0` (`:67-73`). Two different readiness
formulas and two different decay coefficients ship in the same codebase, exposed through two
different endpoints.

**Exceptions and gaps found:**

1. `Quiz` reads use `$or: [{ user }, { isDefault: true }]`. Default quizzes are global by design —
   `user` defaults to `null` (`models/Quiz.js:58-63`) and `defaultQuizSeeder` creates them without
   a user (`defaultQuizSeeder.js:162-170`). Every authenticated user can therefore read every
   default quiz. Intentional, not a defect.
2. `StudyMaterial.findByIdAndUpdate(studyMaterial._id, { $addToSet: { linkedFlashcardSets } })` at
   `flashcardService.js:108` carries **no `user` term in its filter**. It is currently safe only
   because `studyMaterial` was resolved through a user-scoped lookup at `:60` or `:67`. It is a
   latent missing tenant filter, not a live cross-tenant read or write.
3. No per-attempt read endpoint exists; attempts are only surfaced through analytics, tutor
   mistake history, and the recommendation snapshot, all user-scoped.
4. The worker's `SYNC_ATTEMPT` handler re-validates attempt ownership (`worker.js:79-81`) but does
   not re-validate that the quiz still belongs to the user. The quiz is only read, never written.

No missing isolation was found on material, quiz, or attempt queries.

**Per-user AI quota is process-local.** `userAiQuota` keeps its counters in a module-level `Map`
keyed by `label:userId` (`backend/middleware/aiQuotaMiddleware.js:1-46`). Limits are
5 per 60s for quiz generation (`quizRoutes.js:29`), 8 per 60s for flashcard generation
(`flashcardRoutes.js:26`), 20 per 60s for each tutor route (`tutorRoutes.js:21, 28`), and 20 per
60s on the attempt route, labelled "Mistake analysis" (`quizRoutes.js:53`). Because the state is
in-process, the effective limit scales with the number of API replicas, and a restart clears all
counters. The IP-level `aiLimiter` in `server.js:124-130` is similarly in-memory.

**Auth surface.** `signup` and `login` are public; `me` and `PUT /profile` sit behind
`requireAuth` (`authRoutes.js:9-12`). `POST /refresh` and `POST /logout` are deliberately
unauthenticated — the credential is the `refreshToken`, read from an `httpOnly` cookie or the
request body, with rotation on refresh and revocation on logout
(`authController.js:139-175`, cookie options at `:15-22`: `httpOnly`, `secure` in production,
`sameSite: "strict"`, 7-day `maxAge`, path-scoped to `/api/v1/auth`). Neither route has a Zod
schema, unlike the other four.

**Upload accept-list is defined twice and the two disagree.** Multer accepts
`application/pdf`, `text/plain`, and DOCX (`middleware/upload.js:15-19`), while the Zod
`fileSchema` used by `POST /quiz/generate` accepts only `application/pdf`
(`validation/quizSchemas.js:11-14`). The route therefore accepts TXT and DOCX at the multer layer
and rejects them at the validation layer with a 400. Effective behaviour is PDF-only; the
multer filter is dead as written. Size cap is 10MB in both places
(`upload.js:32`, `quizSchemas.js:15-17`).

## 4. Rework Implications

Factual statements about what the current code implies for the rework. No action is taken here.

1. **Documentation should distinguish asynchronous indexing from synchronous PDF extraction and
   quiz generation.** Three separate stages of the upload path have three different execution
   models, and the current documentation collapses them into one "asynchronous pipeline" claim.
2. **`SYNC_ATTEMPT` is the only background job that mutates cumulative counters, and it is now
   guarded rather than naive.** Its cumulative writes run under a conditional per-attempt claim
   inside `runInTransaction` (`worker.js:59-63`, `:72-81`), so a redelivery applies them once and
   a mid-transaction failure undoes them with the claim. Its review-queue effects sit after that
   commit and are replayed and convergent. What reliability work still has to account for is the
   boundary *above* the job: a client that resubmits creates a second attempt, because there is no
   request-level idempotency key, and a job left `not_scheduled` or terminally `failed` is never
   requeued. `INDEX_MATERIAL` and `REBUILD_REVIEW_QUEUE` remain convergent or upsert-based.
3. **Two enqueue failure policies coexist, and neither one is a client error any more.** For
   `INDEX_MATERIAL` and `SYNC_ATTEMPT` the business record is committed first, then the enqueue is
   attempted, and only a `QueueEnqueueError` is absorbed: the endpoint returns its normal 200 plus
   `backgroundProcessing.status: "not_scheduled"` (`quizController.js:36-75`). Any other fault is
   rethrown, so a real bug is never disguised as a scheduling problem.
   `REBUILD_REVIEW_QUEUE` swallows the same error and only logs it
   (`recommendationService.js:42-47`). A client *can* check afterwards — `GET /api/v1/jobs/:id`
   returns the tracked job — and it can also ask for a terminal `SYNC_ATTEMPT` to be re-run at
   `POST /api/v1/jobs/:id/retry`, which is user-triggered recovery rather than automatic
   recovery: nothing re-enqueues a terminal job on its own, and there is no reconciliation
   pass. `/health` exposes raw BullMQ counts only (`healthRoutes.js:36-42`).
4. **Retrieval quality claims must be scoped to the tokenizer.** `local-hash-v1` produces
   non-zero similarity only for shared exact tokens (or hash-bucket collisions). Any statement that
   the retriever "understands" a query is unsupported by the implementation. The existing
   `embeddingService.js:179` lazy-indexing call also means the tutor read path can perform writes.
5. **Retrieval cost is linear in corpus size and runs in the API process.** `MaterialChunk.find(...).lean()`
   loads the whole user corpus for every query (`embeddingService.js:184-186`); the existing text
   index (`MaterialChunk.js:59`) is unused by that code path. There is currently no ANN structure
   of any kind.
6. **The tutor has no confidence signal to gate on.** Retrieval returns only a blended score with
   no calibration, no distribution reference, and no minimum (`embeddingService.js:190-200`), and
   `retrievedContext[].score` is surfaced raw to the UI as a percentage (`src/pages/Tutor.tsx:196`).
   A refusal gate would need a threshold that does not currently exist anywhere.
7. **Quiz quality filtering and non-trivial deduplication exist but sit off the live path.** The
   live upload route imports `generateQuizFromAI` directly (`quizController.js:1`); the filtered and
   ranked pipeline lives in `quizService.generateQuiz`, used only by the seeder. Similarly, there is
   no fallback quiz generator on the live path — a Groq outage is a 500, not a degraded quiz.
8. **No provider seam exists for AI calls.** Both `aiQuizService.js` and `streamingTutorService.js`
   construct `new Groq(...)` inline with a hard-coded model, and `tests/mocks/groqMock.js` is
   unreferenced. CI's offline capability comes from not testing AI code at all, not from a mock
   provider.
9. **Three unit suites validate copies rather than the shipped modules.** `flashcardService`,
   `analyticsService`, and `reviewQueueService` tests re-implement their formulas locally
   (`flashcardService.test.js:8-36`, `analyticsService.test.js:11-50`, `reviewQueueService.test.js:9-76`).
   The measured coverage figures corroborate this: 6.25%, 5.08%, and 12.96% respectively. Any
   change to those services' formulas will not be caught by the current suite.
10. **There is no coverage floor.** The 80% global gate was removed in `e845d65` and current
    measured coverage is 14.40% statements. `docs/ROADMAP.md:53` still lists an "80%+ test
    coverage target" as a next step.
11. **Backend JavaScript is not linted.** `eslint.config.js:11` scopes the config to
    `**/*.{ts,tsx}`; `backend/**/*.js` has no lint coverage, and `npm run build` only performs
    `node --check` on two entry files.
12. **The integration suite can report green while testing nothing about the queue.**
    `bullmq.test.js:14-15` self-skips without `ENABLE_JOB_QUEUE=true`. The default
    `npm run test:integration` script does not set it (`.github/workflows/ci.yml:70` sets it
    explicitly).
13. **Readiness and retention are computed twice with different coefficients**
    (`analyticsService.js:117, 121` vs `recommendationService.js:17, 71`), so the dashboard and
    the recommendation card can disagree for the same learner at the same moment.
14. **Two synchronous rebuild paths still exist** — `POST /review-queue/rebuild`
    (`reviewQueueController.js:20-27`) and `POST /tutor/materials/:id/reindex`
    (`tutorController.js:33-56`) — in addition to the worker-driven ones.
15. **Tenant isolation is intact on every material, quiz, and attempt path.** The one gap is
    `flashcardService.js:108`, which omits `user` from its filter and is currently safe only by
    construction. No isolation defect was found in the audited queries, and none was fixed.
16. **Rate limiting is per-process, not per-user-tenant.** `userAiQuota` stores counters in an
    in-memory `Map` (`aiQuotaMiddleware.js:1-46`), so the effective AI quota multiplies with the
    number of API replicas and resets on restart. If the worker is scaled independently of the
    API, that asymmetry is already in place.
17. **The upload accept-list is defined in two places and they disagree.**
    `middleware/upload.js:15-19` admits PDF, TXT, and DOCX; `validation/quizSchemas.js:11-14`
    admits PDF only. The net behaviour is PDF-only, so the multer branch for TXT and DOCX is
    dead as written.
18. **The Docker images are development images.** `Dockerfile:19` runs `npm run dev -- --host`
    (Vite dev server, no nginx, no build stage) and `backend/Dockerfile:18` runs
    `npm run dev` (nodemon). `README.md:263-265` describes both as production-ready with a
    built bundle served by nginx. Compose does define the three-process topology
    (api / worker / frontend) in `docker-compose.yml`, so the gap is in the images and the
    description, not in the orchestration.
19. **The TypeScript check in CI is not strict for application code.** CI runs
    `npm run typecheck`, which resolves to `tsc -b` over the solution's two referenced projects.
    The effective settings for `src/**` come from `tsconfig.app.json`, not from the root
    solution file: it sets `strict: false`, `noImplicitAny: false`, `noUnusedLocals: false`, and
    `noUnusedParameters: false`, so a passing check does not mean the application type surface is
    sound. The config project is stricter — `tsconfig.node.json` sets `strict: true` — but it
    covers only `vite.config.ts`, `vitest.config.ts`, `playwright.config.ts`, and `tailwind.config.ts`,
    so its strictness says nothing about the application code.
20. **The upload accept-list, the readiness formula, and the retention formula each have two
    definitions in the repository** (items 7, 13, 17). In each case the two are not kept in sync
    by a shared constant or a shared helper.
